# 《心证》项目架构与构建 v1

> 回答一个问题：**你最后要的是一个单体 HTML 推到 GitHub，那开发时该怎么组织？**

---

## 一、结论先说

**开发时拆成 20 来个小文件，交付时用一条命令合成一个 `index.html`。**

不是"先拆了再合"这种多此一举——这里有个真实的取舍：

| | 全程单文件 | 源码分片 + 构建 |
|---|---|---|
| 20 案 + 三幕引擎的体量 | 约 **10000–14000 行**在一个文件里 | 每个文件 200–600 行 |
| 我改代码 | 要在万行文件里定位插入点，改错率高，每次改动的 diff 也难看 | 改哪块进哪个文件，一目了然 |
| 你 review | 打开一个巨型文件找我改了啥 | 看 diff 就行 |
| 案件批量生产 | 20 个案子的 JSON 全塞在代码中间 | `data/cases/c07.json` 一案一文件，能单独校验 |
| 你要的交付物 | 就是它 | `python3 build.py` → 同样是它 |

**构建脚本不引入任何依赖**：一个 `build.py`，只用 Python 标准库，macOS 自带 `python3` 就能跑。不需要 npm、不需要 node_modules、不需要 CI。你在终端敲一句就出货。

> 如果你机器上 `python3 --version` 不通，跟我说一声，我改成纯 `sh` + `cat` 的版本，代价是 JSON 内联要多一步手工。

## 三、`build.py` 做什么

一次构建 5 步，全部是字符串拼接，没有魔法：

1. 读 `src/index.template.html`
2. `<!--INJECT:CSS-->` ← `src/style.css` 原样内联进 `<style>`
3. `<!--INJECT:DATA-->` ← 把 `data/laws.json` 和 `data/cases/*.json` 拼成
   ```js
   const LAWS = {…};
   const CASES = [{…},{…}, …];   // 按文件名排序
   ```
   （JSON 里的 `</script>` 序列要转义成 `<\/script>`，这是唯一的坑）
4. `<!--INJECT:JS-->` ← `src/js/*.js` **按文件名排序**依次拼进一个 `<script>`。文件名前缀的数字就是加载顺序，所以命名必须带序号。
5. 写头部构建注释 + 版本号，输出 `index.html`

```bash
python3 build.py              # → index.html（配 art/ 目录，推 GitHub Pages）
python3 build.py --embed      # → 心证-单文件版.html（art/ 全部转 base64 内嵌）
python3 build.py --check      # 只跑案件包校验，不出货
```

**校验前置**：`build.py` 默认先跑一遍 `validate_cases.py`，任何一个案件包不合法就**拒绝出货**并打印哪一条错了。避免"构建成功但游戏一开就崩"。

**版本注释**：产物头部固定写
```html
<!-- 心证 v1.3.0 · build 2026-09-08T14:22 · 20 cases · SAVE_VERSION=6 -->
```

## 四、关于"单体 HTML"的一个重要区分

你说的"打包成单体 HTML"，实际上有两个不同的东西，我建议**两个都产出**：

### 4.1 `index.html`（主交付物，推 GitHub Pages）

- 代码、样式、法条、20 个案件包**全部内联**，一个文件
- **图片不内联**，走同仓库的 `art/` 目录
- 体积约 **900KB – 1.4MB**
- 双击本地打开能玩（图片走相对路径，`<img>` 不受 CORS 限制），GitHub Pages 上也能玩

### 4.2 `心证-单文件版.html`（可选，用来发给人）

- 连图片一起 base64 内嵌，真正的一个文件走天下
- 体积约 **8–11MB**（68 张 webp 转 base64 会膨胀 33%）

**为什么主产物不内嵌图片**：10MB 的 HTML，浏览器要把整个字符串解析完才开始渲染，手机上首屏会明显卡；分开放 `art/` 则可以并发加载、按需加载、被浏览器缓存，第二次打开几乎瞬开。GitHub Pages 上体验差得很明显。

所以：**日常玩 `index.html`，要发给朋友的时候给单文件版。** 两个产物同一份源码，构建时一个参数的差别。

## 五、GitHub 仓库怎么组织

- **仓库名**：`xinzheng`（或 `courtroom-xinzheng`）。用你现成的 `github-push` 流程推。
- **Pages**：从 `main` 分支根目录发布 → `https://<你的用户名>.github.io/xinzheng/`
- **根目录必须有 `index.html`**，Pages 才会直接把它当首页——这也是为什么产物放根目录而不是 `dist/`。
- **`.gitignore`**：
  ```
  .DS_Store
  *.bak-*
  心证-单文件版.html      # 太大，不进仓库，要发人时本地构建
  src/data/laws-raw/      # 抽法条时的中间产物
  ```
- **提交 `src/`**：一是我改代码要用，二是这个项目的源码本身就值得公开——它是个不错的"单文件 HTML + 自带 LLM 接口"的范例。
- **art/ 进仓库**：68 张 webp 约 7MB，远低于 GitHub 的软限制，没问题。

### 5.1 建议的分支与发布节奏

不搞 dev/main 双分支，你一个人做，`main` 直接推。但：

- **每完成一个批次打一个 tag**：`v1.0-b0`、`v1.0-b1`…，出问题能一键退回
- 每次推送前跑一遍 `python3 build.py --check`
- HTML 头部的构建注释就是版本号，玩家反馈问题时你能对上是哪一版

## 六、README 就是这游戏的门面

推上去之后，README 是所有人看到的第一屏。一期就要写好：

1. **一句话**："你是辩护人。一场庭审，你说的每一句话都会改变法官的心证。"
2. **在线试玩链接**（GitHub Pages 地址）+ 3 张截图（庭审三栏 / 会见室 / 复盘页）
3. **案件列表**——**这里大方用真名**："18 个真实案件改编：许霆案、于欢案、赵春华案、王力军案、陆勇案、快播案、吴英案、张文中案、彭宇案、人脸识别第一案……"（游戏内是化名，复盘页揭示原型，见设计文档 2.1）
4. **怎么接模型**：任何 OpenAI 兼容接口，key 只存本地浏览器，附 DeepSeek 的填法示例
5. **不接模型也能玩**：离线模式说明
6. **致谢**：法条数据来自 [lawtext/laws](https://github.com/lawtext/laws) / [国家法律法规数据库](https://flk.npc.gov.cn)
7. **免责声明**：本作为虚构作品，人物、情节、裁判文书均属虚构，不构成任何法律意见
8. **License**：代码建议 MIT；`art/` 和案件文本另行声明（这部分是你的创作，不适合和代码同一许可）

## 七、迁移路径（从现在的切片到这套架构）

批次 B0 的第一件事，就是把 `庭审模拟器-垂直切片-v0.html` 拆开：

1. 建 `src/` 骨架，把切片的 CSS 原样搬进 `style.css`（**一行不改**，它已经很好了）
2. 把切片的 JS 按职责切进 `js/*.js`，函数体尽量不动
3. 把 `CASE` 常量转成 `data/cases/c01.json`
4. 写 `build.py`，构建出 `index.html`
5. **验收：构建产物的行为与切片逐条一致**（同样的操作序列，同样的心证数字、同样的判决）

这一步不加任何新功能，纯搬家。搬完再开始加三幕。**先把地基换成能承重的，再往上盖。**
